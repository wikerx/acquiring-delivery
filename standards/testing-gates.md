# 测试门禁

## 需求分析阶段

- 明确哪些需求需要单元测试、集成测试、端到端测试、兼容性测试、安全测试或人工验收。
- 支付、代付、退款、回调、MQ、结算、风控、OpenAPI、SDK 和收银台需求必须识别高风险场景。
- 未确认的测试口径进入 open-questions。

## 技术设计阶段

- 后端设计必须列出状态机、幂等、事务、MQ、渠道映射、异常补偿的测试点。
- 前端设计必须列出菜单、权限、路由、接口错误、空状态、加载状态和移动端收银台测试点。
- SDK 设计必须列出兼容性、签名、JWT、AES、RSA、密钥加载、日志脱敏和错误处理测试点。

## 后端开发阶段

- 修改业务规则时必须补充或更新对应模块测试。
- 修改资金、状态、幂等、回调、MQ、OpenAPI 安全链路时必须覆盖成功、失败、重复请求、非法状态和异常输入。
- 修改后至少执行受影响 Maven 模块测试；跨模块影响时执行相关模块链路测试。
- 无法运行数据库、Redis、RocketMQ、Nacos、XXL-JOB 相关测试时，必须记录缺失依赖和未覆盖风险。

## 前端开发阶段

- 修改后执行目标应用 `typecheck` 和 `build`。
- 如存在 lint 脚本，必须执行 lint；当前无 lint 脚本时记录为质量基线缺口。
- 涉及权限、菜单、路由、表格、弹窗、登录、Profile、收银台时必须进行页面级验证。
- 收银台必须覆盖桌面和移动端布局、错误提示、国家/币种/语言切换和敏感数据不落本地存储。

## SDK 开发阶段

- 修改公共 API 或模型时必须保留兼容性测试。
- 修改签名、JWT、AES、RSA、密钥加载、HTTP、JSON、日志脱敏时必须增加对应测试。
- 发布前执行 `mvn test` 和 `mvn package`。
- P3C/PMD 作为规约门禁，使用 `mvn -Pp3c pmd:check`，失败时记录规则和文件。

## 测试阶段

- 测试报告必须包含命令、执行目录、环境、退出码、成功项、失败项和失败原因。
- 不得伪造测试通过，不得用“应该通过”替代命令输出。
- 历史 `target/surefire-reports` 只能作为参考，不得作为本轮验证证据。
- 失败项不得擅自大范围修复；先记录，再由负责人确认处理范围。

## 发布阶段

- 发布前必须有后端、前端、SDK 对应范围的最新验证记录。
- 关键支付链路发布必须保留回归测试清单和回滚验证项。
- 未执行或失败的测试必须在发布资料中明确风险和签署确认。
