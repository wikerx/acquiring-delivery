# 文档门禁

## 需求分析阶段

- 需求文档必须写明来源、背景、目标、范围、不处理项和待确认问题。
- 不确定内容不得写成事实，必须进入 open-questions。
- 不允许把临时讨论直接沉淀为长期规范。

## 技术设计阶段

- 技术方案必须基于真实代码、配置、README、AGENTS 或人工确认。
- 服务职责、模块边界、接口契约、构建命令、环境变量必须提供路径或配置依据。
- 设计结论必须区分“已确认”“需要修正”“待人工确认”。

## 后端开发阶段

- 修改后端代码时，同步更新受影响的 API 文档、架构说明、SQL 草案、配置说明或测试说明。
- 不为小改动新增散落 Markdown，优先更新已有相邻文档。
- 文档不得要求执行数据库变更；数据库变更只能作为 SQL 草案，经人工确认后执行。

## 前端开发阶段

- 前端文档必须明确目标应用目录：`apps/admin-system`、`apps/merchant-portal`、`apps/hosted-checkout`。
- 接口、枚举、状态、错误码说明以后端契约为准。
- 不记录伪造数据、临时 mock 和未确认页面能力为正式功能。

## SDK 开发阶段

- README、配置文档、安全文档、CHANGELOG 必须与 `pom.xml`、公共 API 和测试保持一致。
- 版本号、Tag、变更记录、User-Agent / 常量版本必须一致；不一致时标记待人工确认。
- 示例代码不得包含真实密钥。

## 测试阶段

- 测试报告必须记录执行目录、命令、环境、退出码、成功项、失败项、失败原因。
- 不得用历史报告、猜测或口头描述替代本轮验证证据。
- 构建失败时只记录原因，不擅自修复业务缺陷。

## 发布阶段

- 发布资料必须包含发布范围、版本、变更摘要、验证结果、风险、回滚方案和负责人确认。
- 发布资料不得包含敏感密钥、生产凭证、完整卡号、CVV、Token 或明文敏感报文。
- 未确认项不得进入发布完成结论。
