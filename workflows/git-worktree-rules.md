# Git 和 Worktree 规范

## 文档目的

统一 Acquiring Platform 需求开发中的分支、Worktree、提交、合并、冲突和安全规则。

## 分支命名

| 类型 | 格式 | 示例 |
|---|---|---|
| 需求分支 | `feature/REQ-{需求编号}-{英文简称}` | `feature/REQ-001-payment-routing` |
| 缺陷分支 | `fix/BUG-{缺陷编号}-{英文简称}` | `fix/BUG-001-callback-idempotency` |
| 紧急修复分支 | `hotfix/{日期}-{英文简称}` | `hotfix/20260722-openapi-replay` |

后端、前端、SDK 使用同一需求编号，便于追踪。

## Worktree 使用规则

建议创建独立 Worktree：

- 同一需求需要后端、前端、SDK 并行开发。
- 缺陷修复需要隔离于主需求开发。
- 发布审查期间需要保留稳定代码状态。
- 需要同时比较多个分支实现。

不建议或禁止并行修改：

- 公共 DTO、枚举、数据库实体、Mapper XML、根 `pom.xml`、根 `package.json`、全局配置、权限模型。
- 同一数据库表结构或同一状态机。
- 同一 OpenAPI 协议、SDK 公共模型或加密签名逻辑。

## 公共变更规则

- 公共 DTO、枚举、数据库实体和根配置变更必须在技术设计阶段列明，并经人工确认。
- 公共组件和渠道库不得承载具体商户业务规则。
- 数据库脚本只能提交草案，生产执行必须人工确认。

## 提交信息格式

```text
REQ-{需求编号}: {动词} {简短说明}
BUG-{缺陷编号}: {动词} {简短说明}
HOTFIX-{日期}: {动词} {简短说明}
```

示例：

```text
REQ-001: add payment routing design templates
BUG-001: fix callback idempotency regression
```

## 合并顺序

1. 后端基础契约、数据库草案和配置草案。
2. 前端按稳定契约联调。
3. SDK 仅在适用时合并，并保持兼容性。
4. 测试修复分支。
5. 发布资料和最终状态更新。

## 冲突处理

- 先确认冲突归属和业务含义，再解决冲突。
- 不得为了通过合并删除用户或其他任务的未确认改动。
- 涉及公共 DTO、枚举、实体、接口契约、数据库脚本和配置冲突时，必须回到技术负责人确认。

## 禁止项

- 禁止 Codex 自行推送生产分支。
- 禁止 Codex 未经确认执行强制推送。
- 禁止提交密钥、证书、Token、API Key、真实商户配置、生产凭证或明文敏感报文。
- 禁止在未确认 PRD 和技术设计前创建业务代码提交。
- 禁止混用多个需求编号提交同一变更。

## 完成标准

- 分支、提交和合并均可追踪到需求或缺陷编号。
- Worktree 不造成公共文件并行覆盖。
- 敏感配置未进入 Git。
