# V2 变更和 Desktop 演练

V1 的平台资料、质量门禁、模板与交接规则仍可查阅。V2 增加一个可发现的 Skill、六个独立角色、版本绑定的阶段审批和私有 Git 台账。Code Review 与最终验收成为独立阶段。阶段流转以 [V2 生命周期](requirement-lifecycle.md) 为准，使用 [现行基线](../platform/current-baseline.md) 追溯已有工程约束。

## 演练准备

在 Desktop 选择含 V2 的本地交付项目并打开新会话。准备一个独立的本地 Git 台账和一个可写的合成夹具仓库。夹具只需一个用于修改的文本文件及一次初始提交。权限仅覆盖演练台账和夹具，避免真实后端、前端、SDK 及发布环境。模拟用户决定仅适用于这条演练需求。选择交付 Skill 并确认目标角色可启动。

| 步骤 | 演练输入或动作 | 可观察的结果 |
|---|---|---|
| 创建 | 用 Skill 创建合成需求，例为给夹具文档补充一句标题说明 | 仅产品角色运行。记录原始需求，提交 01 产物并停在待审批。夹具 Git 不变 |
| 无审批及模糊回复 | 发送“继续”或“收到” | 同一审批号、状态和台账 HEAD，夹具 Git 不变 |
| 逐阶段审批 | 每次只对最新审批号批准所显示的下一阶段 | 01 至 07 的决定分别记录。02 批准前没有开发写入。测试、审查和验收为独立实例并引用同一候选 |
| 驳回和重新提交 | 驳回技术设计并明确修订一处，或在测试阶段要求修复已知缺陷 | 保留原审批号和驳回原因。产生新修订号或按范围回流。旧批准不可推进新产物 |
| 跨会话恢复 | 在另一条 Desktop 会话指定同一台账和编号 | 从 Git 读取已提交的状态、证据和决定，等待当前批准或续做已获准但未完成的工作 |
| 重复决定与版本漂移 | 重发已处理的批准。将合成候选替换为新提交后尝试旧批准 | 重复操作不会产生第二条记录或重复执行。旧批准无法推进变更后的候选 |
| 发布准备 | 批准最后一阶段 | 状态为待发布。没有真实发布动作 |
| 冲突保护 | 给演练台账留一处未提交改动或由另一个写会话持有锁，再尝试流转 | 保持已提交的状态并报告阻塞，保留现场 |

验证记录应写明 Desktop 使用情况、Skill 及角色发现、已测试的场景和可重复核对的证据。实际用户批准与合成指令分别注明。发布到公开 PR 的材料只包含脱敏演练结果。命令行或 App Server 观察单独标注。
