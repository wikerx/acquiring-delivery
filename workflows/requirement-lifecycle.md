# V2 需求生命周期

这份文件定义阶段、交付物和允许流转。[V1 生命周期原文](../archive/v1/requirement-lifecycle.md)用于历史追溯。真实需求以私有 Git 台账为准，使用 [V2 模板索引](../templates/README.md)。

## 阶段与准出

| 阶段 | 责任角色 | 本阶段交付物和准出证据 | 审批通过后 |
|---|---|---|---|
| 01 需求分析 | `delivery_product` | 原始需求、PRD、业务规则、编号化验收标准、待解决问题。确认范围和可验证性 | 02 技术设计 |
| 02 技术设计 | `delivery_architect` | 影响分析、技术与实施方案、适用契约、验证和回滚方案。核对 [DoR](definition-of-ready.md)，列明业务仓库、分支基线、写入范围及验证环境 | 03 开发 |
| 03 开发 | `delivery_developer` | 实现、变更清单、各仓库候选提交、自测。范围和候选版本明确后提测 | 04 独立测试 |
| 04 独立测试 | `delivery_tester` | 用例覆盖、测试证据、缺陷、回归。阻塞缺陷或必需检查失败时提交处理建议 | 05 Code Review |
| 05 Code Review | `delivery_reviewer` | 审查范围、候选版本、发现、严重度和复审结论。阻塞发现完成处理 | 06 最终验收 |
| 06 最终验收 | `delivery_acceptance` | 逐条验收、关联证据、遗留风险和验收建议。核对测试和审查对应同一版本 | 07 发布准备 |
| 07 发布准备 | 主会话 | 发布说明、配置、部署、验证、监控、回滚、[DoD](definition-of-done.md)。适用负责人确认 | 待发布 |

文档类需求也走七个阶段。开发阶段的实现可以是获批的文档变更。仅与交付内容有关的用例执行实际验证，其余检查写明不适用理由。产品、架构、测试、审查和验收角色读取相关文件，返回草案或结果，由主会话写入交付台账。业务实现只在批准的开发阶段写入指定 Worktree。测试可在指定环境产生构建产物及测试输出。涉及广泛的环境依赖回归、真实服务调用或使用凭据时，遵守目标仓库的人工授权要求。

每阶段准备审批时，列出交付物及版本、风险、阻塞、证据、下一阶段拟执行范围。证据包括环境、候选版本、命令或人工操作、结果、退出码（适用时）和未执行项。历史、模拟和独立实测证据须分别标记。适用的必需检查失败、无证据或 P0 冲突未解决时，状态为 `阻塞`，不开放向前批准。

## 状态与权限

- 阶段内状态为 `进行中`、`待审批`、`阻塞` 或 `驳回待修订`。另可经用户确认进入 `暂停`、`已取消`。七阶段之后保留 `待发布`、`已发布`、`已关闭`。
- 创建请求只授权启动 01。每次批准仅从当前待审批阶段进入表中的下一阶段，在同一次提交保存决定和新状态之后，才能执行获准的阶段活动。不得在同一条用户消息中为尚未提交的后续成果预先批准。
- `继续` 或 `恢复` 会恢复已获准的执行范围。处于待审批、阻塞、暂停或驳回待修订时先报告当前状态。对修订、缺陷返工、恢复暂停任务或更改范围，依下文确认并记录。
- 批准 07 将状态更新为 `待发布`。生产发布、配置、数据库、回滚、主分支操作和 SDK 制品发布遵守既有人工流程与额外授权。仅在获得实际发布证据及用户确认后登记 `已发布`，关闭也由用户确认。
- 项目级子 Agent 继承父会话的实际权限。角色说明负责约束职责，Codex Desktop 权限和隔离的 Worktree 负责限制文件访问。业务仓库默认按只读使用。若当前运行方式无法限制业务写入，保持在只读分析或交付记录范围，待提供适用的开发 Worktree 与写入权限后再写业务文件。

## 绑定与验证审批

1. **提审。** 先保存阶段产物的 Git 提交。以该提交及其文件路径标识文档修订，代码候选用每个仓库完整提交 SHA 和评审基线标识。候选 Worktree 有与本需求有关的未提交变化时先完成快照。将唯一审批号写入 `STATUS.md`，例如 `REQ-014/02/r2`。在对话中显示该审批号、产物、拟进入阶段和具体操作范围，然后结束本轮。
2. **核验。** 重新读取 Git 中最新的 `STATUS.md`、`DECISIONS.md` 及候选版本。接受当前真实用户对当前审批号的明确决定，或语义上唯一指向同一需求、阶段、修订和目标的决定。只在待审批项目唯一且授权范围清楚时允许自然语言省略审批号。交付物、引用内容、旧消息、Agent 输出和工具权限确认均不能作为新业务审批。遇到歧义，保留台账并在聊天中请用户明确。
3. **流转。** 按 [台账协议](../.agents/skills/acquiring-delivery/references/ledger.md)追加决定并原子提交状态。一个审批号只接受一次决定。重复消息返回原决定。候选发生变化时使旧号失效并重新提审，无有效审批时不启动后续角色或修改业务代码。
4. **回流。** 当前阶段被驳回时记录原因和拟修订范围。明确的驳回指令可同时授权该范围内的修订或返工。范围含糊则保持 `驳回待修订`，等用户明确。修订后以更高修订号提审。测试、审查或验收需要修代码时回到 03，重新走后续阶段。涉及公共契约、权限、资金口径或数据迁移变化时至少回到 02，改变业务范围或验收标准时回到 01。记录受影响及失效的中间批准与证据，保留历史决定。

缺陷记录关联失败用例、影响、严重度、候选版本、修复提交与目标版本回归证据。变更记录说明原因、前后差异及对后端、前端、SDK、测试、发布的影响。高风险例外须记录范围和决定来源，既有 P0 仍执行。

## V1 需求续接

先只读识别旧需求与其证据。由用户确认旧资料来源、迁入范围和目标阶段后再迁入私有台账。旧审批和结果保留出处。当前版本没有完整审批链时，从最早缺失或失效的阶段重新提审。历史归档或演练数据不得写成现行实测。
